🔴 严重 C-02 逻辑

松手后 onWake() 仍可能触发——意外结束哄睡

@/Users/fanhui/Desktop/github/SleepWhisper-android/app/src/main/java/com/lizhi1026/sleepwhisper/features/sleeping/SleepingScreen.kt:370-390
// SleepingScreen.kt:371-390
val job = scope.launch {
    fillProgress.animateTo(1f, tween(durationMillis = SWMotion.longPressMs.toInt()))
    if (fillProgress.value >= 0.99f) {
        delay(420)        // ❌ 这 420ms 期间无论是否松手都会触发
        onWake()
    }
}
while (true) {
    val ev = awaitPointerEvent(PointerEventPass.Main)
    if (ev.changes.all { !it.pressed }) {
        if (fillProgress.value < 0.99f) {
            job.cancel()
            scope.launch { fillProgress.animateTo(0f, tween(200)) }
        }
        break          // ❌ ≥0.99 松手时未取消 job
    }
}
为什么不合理：当动画到 99.5% 用户松手时（这 100ms 临界窗口内），父级 while 检测到 !pressed，但因 fillProgress.value ≥ 0.99f 不取消 job。子协程的 delay(420) 仍在进行 → 自动调用 onWake()。父母明明只是手抖松开，宝宝的睡眠却被结束。
建议修复：① 删除 delay(420)；② 松手 break 之前无条件 job.cancel()；③ 完成判定改用 animateTo 的协程返回值，而不是再读 .value 二次判定。
🔴 严重 C-05 交互

长按唤醒阈值仅 600ms，是普通长按而非"防误触长按"

SWTokens.kt:48 longPressMs = 600L

图 3：黑暗中摸手机 0.6s 即可结束睡眠
为什么不合理：结束睡眠是破坏性操作（不可逆地写入 endAt），iOS HIG / Material 都建议此类操作长按 ≥ 1.5s 并配触觉确认。当前 600ms 与系统普通长按等同，半夜摸手机充电时极易触发。

🔴 严重 C-07 逻辑

为什么不合理：pause 时记录 remaining = endsAt - now。若后台进程被杀重启，remaining 从持久化加载，已经是过去时；resume 时 endsAt = now + remaining 可能仍 ≤ now，scheduleAutoStop 立刻触发 stop——用户以为按了"继续"，结果音乐瞬停。
